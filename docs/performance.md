# 性能与内存

[文档导航](README.md)

优化应先识别耗时位于传输、软件驱动还是面板等待，再决定是否付出 Flash/RAM 成本。本项目已采用全局 `-O2 + LTO`、较短的 BUSY 就绪尾延迟和连续 SPI 数据写入；当前仍受面板刷新时间和紧张的 RAM 预算约束。

## 内存先看三种不同指标

| 指标 | 如何取得 | 能说明什么 |
| --- | --- | --- |
| 应用 Flash 末端 | 构建后 `scripts/check_memory.py` | 所有加载镜像是否在 126 KiB 应用分区内，含 RAM 初始化镜像 |
| 静态预留 RAM | ELF PT_LOAD 与构建报告 | 数据、缓冲、线程栈是否在 16 KiB 内 |
| 运行栈未使用前缀 | 匹配 ELF 的栈符号 + 运行后 RAM 填充值 | 某个负载下栈曾触及的位置，不是所有路径的证明 |

构建成功后可使用 Zephyr 原生报告定位具体模块和符号：

```sh
export ZEPHYR_BASE="$PWD/.deps/zephyr"
uv run --locked west build -d build -t rom_report
uv run --locked west build -d build -t ram_report
uv run --locked west build -d build -t dashboard
```

报告用于归因；`scripts/check_memory.py` 仍负责本板的 126 KiB 应用分区、16 KiB RAM 和复位向量检查。

动态堆为零。静态 RAM 之外的余量不等于主线程可用栈；反过来，主线程还有未使用前缀，也不能拿来新增全局缓冲。

2026-09-18 的无补丁 Zephyr `v4.4.2` 构建（Arm GNU GCC 15.3.1 20260627、
全局 O2 + LTO、硬件 AES、主栈 1280 B）结果如下，尚无新版实机栈测量：

| 屏幕模式 | Flash B | RAM B | 静态区外剩余 RAM B |
| --- | ---: | ---: | ---: |
| 默认 deep sleep | 109524 | 16360 | 24 |
| power-off 对照 | 109484 | 16360 | 24 |

该工具链的 ELF `rodata` 节带有 WRITE 标志，但物理地址位于 Flash；原生 `ram_report`
会误计入 RAM。报告和 dashboard 适合查符号，容量判断使用链接器及 `check_memory.py`
的实际加载地址；LTO 也会使部分符号失去源文件归属。

2026-09-16 的帧数配置构建报告为 121,036 B Flash / 16,376 B RAM，预留区外剩 8 B；这是历史样本，不是其他工具链或后续代码的保证。每次以当前构建输出为准。

2026-09-12 全局 O2、主栈 1,600 B 的候选在完整加密回归后观察到：

| 栈 | 预留 B | 未使用前缀 B |
| --- | ---: | ---: |
| main | 1600 | 156 |
| system workqueue | 1024 | 436 |
| controller RX | 768 | 516 |
| priority RX | 448 | 220 |
| ISR | 1024 | 520 |
| idle | 128 | 84 |

线程哨兵完整，ISR 不设哨兵。该数据不覆盖后续所有改动、最坏中断嵌套或故障组合；减栈必须重新测量，不能引用这张表当通用余量。

## 默认编译策略为何可行

全局 O2 初始候选曾超过 Flash；裁掉未使用系统功能后才成为可用默认。当前配置在 [prj.conf](../prj.conf)，不要重新采用旧实验中“仅 epd.c 为 O2”的方案作为现状。

裁剪包括厂商 HCI、详细蓝牙断言字符串、多属性读取、远程写设备名、未使用控制过程、legacy 广播切换备份和时间片支持。两点必须与裁剪一同保留：

- 去掉厂商 HCI 后，应用在 `bt_enable()` 前从 FICR 建立固定 BLE 身份，否则可能每次启动换地址。
- Zephyr 4.4.2 已将 ATT 地址格式化放进日志宏，无日志构建无需旧的 ATT 补丁，仍保留超时断开。

依赖版本通过 `west.yml` 的 Zephyr tag 和导入的 manifest 固定。直接改 `.deps/` 不构成可复现交付。保留认证、MTU 247 与协议校验；原生池数量和栈预算的调整见下文。

O3 曾超资源，Oz 在当时工具链与 Os 产物相同；这些都是候选实验结果，不能泛化为所有编译器的规律。更换优化等级应同时检查实际编译命令、ELF、栈及代表性负载。

## 无补丁的内存预算

Zephyr 依赖使用未修改的正式 tag，不再维护或自动应用 Bluetooth 缓冲池补丁。
在 `dbb00ad` 的 TinyCrypt 基线上，仅取消补丁会超出 RAM 948 B。
以下组合保留 MTU 247、认证、流式 zlib 和应用单命令队列，使原生缓冲实现可链接：

- AES 使用控制器的 `bt_encrypt_be()`，CMAC/CCM 保持主机可测；认证 CMAC 分支已知
  调用帧从 1288 B 降到 916 B，主栈预算从 1600 B 调至 1280 B，回收 320 B。
- 解压 literal/length 符号表从 16 bit 改为 9 bit，小字母表改为 8 bit。512 B 滑动窗口
  和符号范围保留，inflater 状态从 1516 B 降至 1232 B，计入链接对齐后回收 288 B RAM。
- ACL TX 从 2 调为 1，Event RX 从 3 调为 2，回收 364 B。事件数量仍大于 ACL TX。
  ACL RX extra=1、ATT TX=1、L2CAP TX=2 以及分片池保持原值。

合计回收 972 B，使取消补丁后的 17332 B RAM 降至 16360 B。
这不是保持全部队列预算的等价变换：发送并行度降低，池耗尽、吞吐、无线重传与重连须实测。
916 B 也不是整个主线程的最大栈消耗；更深的通知链、协议回调、启动包装和异常现场仍需覆盖。
1280 B 主栈通过构建和主机测试，尚无此版本的实机水位证据；旧的 1600 B 栈实测不能证明它安全。
控制器 RX 栈保持新版默认 896 B，其他线程栈未缩小。

单独换硬件 AES、仍保留 1600 B 主栈时，Flash 从 110920 B 降至 109392 B，
静态 RAM 不变。压紧表在同一硬件候选上增加 224 B Flash，以少量解码指令换 RAM。
密码学实现与测量限制见[硬件 AES 与 RAM](crypto-memory-options.md)。

`BT_RECV_WORKQ_SYS` 已启用，不能再靠合并 host RX 线程省出另一份栈。
实验中只打开 HCI ACL flow control 会增加接收/命令缓冲，超出量从 948 B 增为 1668 B，
不能替代原补丁。降 MTU 虽可链接，但 SDK 的加密配置首包需要至少 MTU 236，因此未采用。

旧检出中的 `.deps/zephyr` 可能还留有上一版补丁。切换到无补丁构建前，先检查
`git -C .deps/zephyr diff`，确认只有已知补丁时可用历史版本撤销：

```sh
mkdir -p build
git show dbb00ad:scripts/patches/zephyr-4.4.2-compact-buffers.patch > build/legacy-buffers.patch
git -C .deps/zephyr apply --reverse "$PWD/build/legacy-buffers.patch"
```

全新依赖无需这一步；已经撤销时也不要重复运行。存在其他依赖修改时先分别处理，
不要为构建直接丢弃本地修改。正式验证使用 `scripts/build.py --setup --pristine`、
`scripts/test.py` 和 power-off 对照构建。随机 zlib 流测试覆盖分包边界和不同 Huffman 表。

## 把刷新时间拆开

```text
SDK 调用开始 → START ACK → END ACK → 刷新完成 00 73
               初始化      数据传输      面板等待、关电及通知
```

这里的主机时间包含 BLE、调度和客户端开销，不是纯 CPU cycles；END ACK 后也不是纯 BUSY 时间。连接/发现耗时应单独测量。

早期同板负载中，raw 全刷中位数 4.872 s，其中 END ACK 后 3.821 s；zlib 把应用传输字节减少约 46.5%，总时间只降约 1.5%。这解释了为何只优化压缩吞吐难以按相同比例缩短显示时间。

BUSY 就绪后的尾延迟从 200 ms 改为 10 ms，正常全刷三处名义减少 570 ms；保留 SPI 最小半周期、中断、刷新命令后的等待和有界超时。连续片选减少数据块的 GPIO 操作，但其独立端到端收益不足以从少量样本中分离。面板时序仍需画质、全温区与低电压验证。

## 已有实验支持什么判断

以下为 2026-09-12 的 Zephyr 同板测量，使用 Arm GNU GCC 15.3.1 20260627，各项是三次中位数，单位秒。固定 2,756 B 图片、局部窗口 `(32,64,32,16)`，macOS、SDK 7.14.1、MTU 247，客户端请求窗口/ACK 2，固件实际协商 1。计时期间无运行中的调试会话。

| 候选 | raw 全刷 | zlib 全刷 | 局刷 | raw START ACK |
| --- | ---: | ---: | ---: | ---: |
| 初始基线 | 4.872 | 4.799 | 2.907 | 0.433 |
| 尾延迟与 SPI 分组后 | 4.302 | 3.915 | 2.352 | 0.241 |
| 仅 EPD O2 | 4.003 | 4.015 | 2.308 | 0.135 |
| 全局 O2 与系统裁剪 | 4.002 | 3.688 | 2.310 | 0.148 |

EPD 编译优化对初始化前段的收益比总耗时更稳定；完整刷新阶段存在约 0.3 s 波动。全局 O2 的最终性能轨迹采自增加主栈 64 B 前的同代码候选，之后主栈版本另做了加密回归。不可把表中某个下降百分比承诺给所有图片或版本。

同轮修复后的 Mynewt 全局 O2 对照为 raw 4.345 s、zlib 4.394 s、局刷 2.426 s，使用临时测试身份避开 macOS GATT 缓存。两套固件还存在驱动、启动与调度差别，不能据此把差值全归于 RTOS；早期 Mynewt 时钟卡死样本更不能混入正常性能排名。本仓不依赖另一个仓库即可构建和验证。

## 可复用的测量流程

1. 冻结源码、完整编译命令、ELF/HEX/BIN、哈希和内存报告。版本 SHA 不含未提交修改。
2. 固定设备、供电、温度、图像、局部窗口、客户端和 MTU；局刷前用一致全刷建立 etag。
3. 每类重复测量，记录各阶段、成功/失败次数和离散范围，每次以收到 `00 73` 为协议成功条件；另做目视或光学检查。
4. 基准计时与调试采样分开。运行中 PCSR/DHCSR 采样可定位 WFI、SPI、解压等热点，但采样比例不是精确 CPU 利用率，更不是功耗。
5. 栈测量使用设备上同一 ELF；转储 RAM 前后的 halt/reset 应记录，跳过任务栈哨兵后扫描填充值。新增诊断本身会改变内存与时序。

已有 PC 采样中快广播空闲窗口约 99% 命中 WFI，这说明大量等待，不支持续航排名。电流方法见[电源](power.md)。历史对照脚本位于未跟踪的 `build/profiling-20260912/` 等目录，不能作为新检出的可执行前提；正式回归入口见[验证指南](validation.md)。
